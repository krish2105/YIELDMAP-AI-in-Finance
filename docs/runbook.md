# Runbook

What to do when something is wrong, written for the person on the other end of an alert — who may
be you in six months with no memory of any of this.

## First: what is actually broken

```bash
curl -s https://yieldmap-api.onrender.com/health | python3 -m json.tool
```

```json
{
  "status": "ok",
  "database": { "present": true },
  "auth": { "configured": true },
  "store": { "durable": false }
}
```

Four facts, and each one fails differently:

| Symptom | What it means |
|---|---|
| No response for ~50s, then 200 | Normal. The free instance sleeps after 15 minutes idle. Not an incident. |
| No response after 90s | The instance is down or the build failed. See **The API is down**. |
| 200 with `database.present: false` | The service is up and has no data. Every page will show errors. See **No data**. |
| 200 with `auth.configured: false` | Reads work, writes are unreachable. See **Nobody can sign in**. |
| `store.durable: false` | Expected today. Memos are lost on restart; see `docs/limits.md`. Not an incident. |

The web app is separate: if the site loads but every panel errors, the front end is fine and the
API is not — check the above first.

## The API is down

1. **Look at the deploy, not the code.** Render dashboard → `yieldmap-api` → Events. A failed
   build leaves the previous version running; a failed *start* does not.
2. **The most likely cause is deliberate.** With `YIELDMAP_ENV=production` the service refuses to
   start when `AUTH_SECRET` or `YIELDMAP_USERS` is missing, and says which in the logs. That is a
   config error masquerading as an outage, and it is meant to be loud. Set the variable; it
   redeploys itself.
3. **Otherwise read the logs.** They are JSON, one line per request, with a `request_id`. Filter
   for `"level":"error"`.
4. **Roll back** from the Render dashboard if a deploy broke it. The previous image is one click.

## No data

The warehouse is rebuilt during the container's build, so an empty database means the build
skipped it or the drop was missing.

```bash
uv run python -m scripts.build_all --synthetic --force   # locally, to reproduce
```

If that works locally, the build command on Render is the problem. If it does not, the raw drop is
missing — see `docs/loading_real_data.md`.

## Nobody can sign in

- `auth.configured: false` means `AUTH_SECRET` or `YIELDMAP_USERS` is unset. Both are Render
  dashboard values; `AUTH_SECRET` is generated by Render and should not be typed by hand.
- **Everyone signed out at once** after a restart: `AUTH_SECRET` is not set, so each process
  generates its own key and tokens do not survive. This is exactly what the startup check is for,
  so check it did not get switched off.
- **One person cannot sign in**: their entry in `YIELDMAP_USERS` is malformed. The format is
  `email:role:argon2-hash`, semicolons between entries, and a malformed entry is *ignored* rather
  than trusted — so a typo silently removes an account rather than creating a privileged one.

  ```bash
  uv run python -m api.auth hash 'the-password'
  ```

## Everything is slow, or answers stopped

Check `/ask/providers`. If every backend reads `skipped`, the chain has nothing left and answers
degrade to a refusal.

- `daily request budget spent` on a **metered** backend is working as designed: the free tier is
  spent for the day. It resets at midnight UTC.
- The same message on the **fake** backend would be a bug — it spends nothing and is exempt. That
  was a real defect once: it silently turned every answer into a refusal.

## The nightly ingest failed

Actions → Ingest DLD open data. The job is expected to fail at the download step while the
publisher blocks datacenter addresses; that is recorded, not an incident. What matters is whether
`docs/results/source_probe.json` changed — if a host that used to time out now answers, the data
ladder has moved and `docs/loading_real_data.md` needs revisiting.

## An uptime issue opened itself

`.github/workflows/uptime.yml` probes `/health` every half hour and files an issue labelled
`uptime`, then closes it on recovery. One issue per condition rather than one per probe. If it is
open and the service is fine, the probe is wrong — check it is not timing out on the 50-second
cold start.

## A deploy went to a branch nobody is on

`render.yaml` declares `branch: main`, but the live service was created against the feature branch
before the blueprint existed and Render does not reconcile the two on its own. Once the pull
request merges, the branch it watches stops receiving commits and the API quietly freezes at
whatever was last pushed there — it stays up, serving old code, which is the failure that does not
page anyone.

Fix it once, in the dashboard: **Render → yieldmap-api → Settings → Build & Deploy → Branch →
`main` → Save**. Confirm with `list_services`, or by checking the next commit to `main` triggers a
deploy. The same applies to Vercel, which takes production from the repository's default branch
and needs no action.

## Memos are being lost on restart

`GET /health` reports `store.durable`. When it is `false` the API is writing memos to the
container's disk, which a free-tier instance discards on every restart and sleep — silently, and
with no error anywhere.

The fix is `DATABASE_URL`. It points at the Supabase project shared with RAQIB, and YIELDMAP's
tables live in the `yieldmap` schema rather than `public`, which RAQIB owns. That isolation is
enforced twice over: every statement names the schema, and each pooled connection pins
`search_path` to it. The first is what makes it correct behind a transaction pooler, where session
state does not survive between statements.

To set it up from scratch:

1. **Supabase → the project → Connect.** Take the **session pooler** URI (port 5432) or the direct
   connection. The transaction pooler (6543) also works, but the session pooler is the better fit
   for a long-lived connection pool.
2. Substitute the database password into it. Supabase does not display it after project creation —
   reset it under Settings → Database if it is not to hand.
3. **Render → yieldmap-api → Environment → `DATABASE_URL`** → paste → Save. `DATABASE_SCHEMA` is
   already `yieldmap` from the blueprint.
4. The service redeploys. Confirm with `GET /health`: `store.durable` is `true` and
   `store.schema` is `yieldmap`.

The schema and its table are created on first connection if absent, so there is no migration step.

## What has no procedure yet

Said plainly, because a runbook that pretends to cover everything is worse than one with gaps:

- **No paging.** Issues and Sentry, both of which someone has to look at.
- **No rollback for data.** The warehouse is rebuilt, not backed up. A bad drop is fixed by
  loading a good one.
- **One region, one instance.** There is nothing to fail over to.
